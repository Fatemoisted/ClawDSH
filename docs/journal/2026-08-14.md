## 排查记录：首次 typecheck 失败与修复

- **现象**：`pnpm run typecheck` 在 tsdown host 阶段报 `[clawdsh] Cannot find entry: lib/types/{index,invariant,startup}.js`。
- **根因**：tsdown 的 workspace 扫描以**目录**为粒度（`onlyDirectories: true`），`packages/openclaw/*` 骨架目录被扫中；目录内无 package.json → 向上寻根到根包（name=`clawdsh`）→ 用根配置解析入口失败。此前"骨架不放 package.json"策略只防住了 pnpm，未防住 tsdown。
- **修复**：根 `tsdown.config.ts` 的 workspace 改为对象形式并显式 `exclude: ['packages/openclaw/**']`（exclude 会整体替换 tsdown 内置默认值，四条默认模式已原样保留）。该改动已写入 ADR-0001 决策 4 的"构建编排最小豁免"。

## 阶段 2 收尾：渠道适配器 SDK 化重构（发起人方向，2026-08-14）

- **背景**：初版 channel-feishu 手搓 `node:http` webhook + 裸 `fetch` 调 im OpenAPI、channel-telegram 手搓 getUpdates 轮询。发起人指正：应「先看 OpenClaw 本身如何实现，再看如何接入 Cordis 模块化设计」，避免手搓出错（飞书有权限/长连接等繁琐程序）。
- **飞书 SDK 化**：改用官方 `@larksuiteoapi/node-sdk`（`^1.73.0`）——`Lark.EventDispatcher` 注册 `im.message.receive_v1` + `Lark.WSClient` 长连接入站（SDK 鉴权 + ACK，按 `message_id` 幂等去重）；`Lark.Client.im.message.create` 出站（tenant token 归 SDK `tokenManager`）。**长连接取代 webhook**：删 `port`/`path`/`encryptKey`/`verificationToken` 四个配置，新增 `domain`（feishu/lark）。
- **Telegram SDK 化**：改用 `grammy`（`^1.45.1`）——`Bot.on('message:text')` + `bot.start({allowed_updates:['message'], timeout})` 长轮询入站；`bot.api.sendMessage` 出站；offset 归 grammY 长轮询循环，适配器不再自持状态。
- **Cordis 契约不变**：两者仍是函数插件（named-export `name`/`inject`/`Config`/`apply`）+ `ChannelAdapter` 契约 + `ctx.effect(() => ctx.channels.registerAdapter(...))` 注册；`start()` 返回 disposer（飞书 `wsClient.close({force:true})`、Telegram `bot.stop()`）。测试注入 seam（`AdapterDeps.client`/`AdapterDeps.bot`）保持协议映射可测。
- **原则入册**：`docs/standards/plugin-contract.md` 新增「§8 OpenClaw 功能移植原则——先看实现，再接入 Cordis」（先读上游出处 → 再选 seam/形态 → 优先复用上游已验证的 SDK，禁止手搓底层协议）。
- **验证**：feishu 契约测试 9/9、telegram 7/7、全量 `pnpm typecheck` 绿、`gen-config-catalog` 再生成。
