## Telegram 带凭证端到端验证

### 凭证处理与组装

- 本轮通过 `TELEGRAM_BOT_TOKEN` 凭证引用使用专用 Telegram bot，并通过 `DEEPSEEK_API_KEY` 使用 Harness 模型。本日志与仓库均不记录 token 或 chat id。
- 仓库外的 profile overlay 启用 Telegram，并禁用飞书/Discord 以隔离测试。随附 profile 中 Telegram 仍为 opt-in，并指定 `botTokenEnv: TELEGRAM_BOT_TOKEN`；其中的 Ark embedding 行指定 `apiKeyEnv: ARK_API_KEY`。
- daemon 测试前用 Bot API `getMe` 直接探针确认身份。配置 dump 仍只是组装检查，不是鉴权证据。

### 已通过路径

- 私聊：`/start`、精确的唯一 marker 回复，以及原生 reply-to-source 投递。
- 持久 Memory：写入一项事实，干净停止 daemon，再以同一 `DSH_HOME` 重启后召回同一事实。
- 群聊路由：未 mention 消息被门控；用户名 mention 与 reply-to-bot 被准入。
- 命令路由：`/help@BotUsername` 保留 `/help`；指向其他 bot 的命令被隔离。
- Harness 工具执行：时效性问题经 `web_search` 完成并回传 Telegram。
- 消息规范化：带定向文本的媒体 caption 达到模型，无正文媒体被忽略。
- 传输与恢复：离线补收、超过 4096 UTF-16 unit 的 Unicode-safe 分片、中断回合恢复与同一聊天 FIFO 均完成。

### Memory 与恢复证据

本轮刻意不提供 `ARK_API_KEY`。`memory_search` 以缺凭证错误 fail-loud，随后 agent 使用更窄的 `memory_get` 回退读取已存事实。干净重启保留了持久会话；另一次被中断的轮次在下一次启动时恢复；离线期间发送的消息在 polling 恢复后补收；同一 chat 快速准入的两条消息按 FIFO 顺序完成。

### 负向门控

- 在 Telegram 已配置为把普通群消息投递给测试 bot 的前提下，未定向普通群消息既不产生 ack，也不产生模型回复。
- 指向不同 bot 的命令不算对当前 bot 的 mention。
- 既无文本也无 caption 的媒体不会创建模型轮次。

### 覆盖边界

- 尚未在真实 Telegram forum topic 中测试。Topic 传递与隔离仍只有无密钥契约覆盖，直至真实客户端行通过。
- Ack reaction 有无密钥契约覆盖，但本轮带凭证测试未独立观察。
- 托管凭证热切换、缺凭证时关闭 capability、永久停止 polling 的行为，以及 chat-id 迁移 alias 均不计为本轮线上通过。无密钥覆盖验证 401 会关闭 receive/send/react，而 409 只关闭 receive。
- 本次线上测试当时的 adapter 会转发媒体 caption，并忽略无正文媒体；它不会下载图片字节。本段只记录受测构建的实际观察，不能作为后续 attachment 实现已通过线上的证据。
- 长轮询的 FIFO 仍只在进程内成立，且没有持久 provider inbox/outbox 或事务式多分片投递。

### 基线之后的无密钥实现

线上测试之后，当前实现新增了短暂 photo/图片 document source 与 adapter materialization 钩子。无密钥测试覆盖 PNG/JPEG/WebP/GIF document 映射、最大 photo 选择、先通过群聊准入与模型模态检查再 materialize、下载前拒绝 provider 声明超限、由官方 `@grammyjs/files` hydrate `getUrl`，以及在 Harness `ctx.attachments` 导入前通过原生 `fetch` 在可取消 deadline 下流式读取。测试还覆盖图片模型使用持久引用、文本模型 caption 携带图片省略上下文继续，以及纯图片固定提示且不创建模型轮次。实现会限制实际读取字节，在保存任何引用前校验全部选中输入，并提供 `imageDownloadTimeoutMs`：默认 30000 毫秒，可配置范围为 1000–2147483647。这些都不是带凭证真实客户端通过项；随附的 DeepSeek selection 只支持文本，因此不会下载 Telegram 图片字节。

当前迁移实现还通过无密钥测试覆盖了预配置 alias 路由、无 alias 迁移 service update 之后的内存暂停，以及无效 alias 拒绝。该暂停仅为 best effort：Telegram 可能先投递新 id 的普通流量，restart/remount 也会丢失暂停集合。只有在新 id 流量前配置 alias，才能保证复用旧的持久 session 身份。

### 结果

带凭证基线已闭环真实 Bot API 上的 Telegram 私聊/群聊文本路由、Harness agent/模型/工具、持久 session 与 Memory 层，以及出站投递。准确可复现的流程、失败信号与非基线行见 [Telegram 端到端实操手册](../cookbook/telegram-e2e.md)；包级行为与限制仍以 [Telegram adapter README](../../packages/openclaw/channel-telegram/README.md)为准。
